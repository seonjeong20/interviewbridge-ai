## 요약

"코드로 확정할 수 있는 것은 코드로, 의미 판단만 LLM으로"라는 원칙으로 검증 단계를 다시 만들어 두 번 측정했습니다. 처음 만든 판(v2.0)과, 그 실패를 분석해 고친 판(v2.1)입니다. 결과는 한쪽으로 깔끔하지 않습니다.

| 지표 (기존 17건) | 기존 Reviewer | v2.0 | v2.1 |
| --- | --- | --- | --- |
| 삽입 결함 해소 | 19/45 | 14/45 | 27/45 |
| 정상 평가 보존 | 30/30 | 28/30 | 20/30 |
| 정상 평가를 원문 그대로 통과 | 0/30 | 28/30 | 20/30 |
| 항목 점수 변경 | 5/85 | 0/85 | 0/85 |
| 종합 점수 산술 오류가 남은 최종 평가 | 10/85 | 0/85 | 0/85 |
| 답변에 없는 사실이 남은 평가 (TC-13) | 5/5 | 4/5 | 0/5 |
| 코칭까지 전파된 오류 | 4/21 | 3/21 | 0/21 |

확실하게 개선된 것은 세 가지입니다.

1. **종합 점수 산술 오류는 코드 검사로 전부 해결됐습니다.** 기존 Reviewer가 한 번도 고치지 못한 오류를 Validator가 LLM 호출 없이 모두 고쳤습니다(합성 5/5, 보조 케이스 3/3, 실제 Evaluator 출력 7/7).
2. **재작성을 없애자 정상 평가가 원문 그대로 통과합니다.** 실제 Evaluator 출력 51건에서 기존 Reviewer는 45건의 문장을 바꿨고, v2.0은 산술 수정 7건 외에는 한 글자도 바꾸지 않았습니다. 이때 검토 시간은 평균 3.8초에서 0.6초로 줄었습니다.
3. **답변 원문을 주자 답변에 없는 사실을 근거로 든 평가를 잡아냈습니다.** v2.1은 TC-13에서 이를 5회 모두 제거했고, 그 결과 코칭 모범 답안에 없는 경력이 서술되는 일이 3/3에서 0/3으로 사라졌습니다.

개선되지 않았거나 나빠진 것도 분명합니다.

1. **v2.0은 결함을 찾고도 고치지 못했습니다.** 탐지는 55회 중 50회였지만 해소는 14/45로 기존(19/45)보다 낮았습니다.
2. **v2.1은 해소율을 높인 대신 정상 평가를 손상시켰습니다.** 서로 다른 약점을 중복으로 보고 삭제한 실행이 정상 케이스 30회 중 10회, 실제 Evaluator 출력 51건 중 18건입니다. 기존 Reviewer에는 없던 문제입니다.
3. **점수가 틀린 경우(TC-08)는 설계상 고치지 않습니다.** 지적은 5/5 했지만 기존 Reviewer가 5/5 해소하던 케이스가 0/5가 됐습니다.

결론: **Deterministic Validator와 "재작성 대신 발견 사항"이라는 구조는 적용할 근거가 있습니다. v2.1 전체를 그대로 서비스에 넣을 근거는 없습니다.** 상세는 12, 13절에 있습니다.

모든 비율은 합성 케이스(기존 17건, 보조 8건)와 1차에서 수집한 실제 Evaluator 출력 51건에서 나온 값이며 일반적인 성능 수치가 아닙니다. 출력을 읽고 내린 판정은 **AI-assisted adjudication**(실험을 수행한 AI 코딩 에이전트의 판독)이며 사람이 검토한 결과가 아닙니다.

## 1. 1차 실험에서 확인된 문제

1차 보고서의 수치를 측정 방법, 분모와 함께 다시 적습니다. 이 값이 개선 전 기준입니다.

| 문제 | 1차 값 | 분모와 측정 방법 |
| --- | --- | --- |
| 삽입 결함 해소 | 19/45 | 탐지 가능 결함 9건(TC-07~11, 14~17) × 5회. 최종 평가를 읽고 판정 |
| 정상 평가 보존 | 30/30 | 정상 6건 × 5회. 점수와 의미 유지 |
| 코칭 오류 전파 | 4/14 대 4/14 | 7건(TC-07~11, 13, 16) × 2회. 코칭을 읽고 판정 |
| summary 모순 해소 | 0/10 | TC-07, TC-16 × 5회 |
| 항목 간 모순 해소 | 1/10 | TC-10, TC-11 × 5회 |
| 산술 오류 수정 | 0/10 | TC-17 5회 + 실제 Evaluator 출력 중 오류 5건 |
| 답변에 없는 근거 통과 | 5/5 | TC-13 × 5회 |
| Reviewer 응답 시간 | 약 3.2초 | 138회 실행 평균 |
| LLM Judge 판정 | 38/45 (판독 19/45) | `gpt-4.1-mini` |

기존 Reviewer의 구조적 원인은 여섯 가지였습니다. (1) 질문과 답변 원문을 받지 못함, (2) 평가 JSON 전체를 다시 씀, (3) 무엇을 고쳤는지 남지 않음, (4) 정상 평가도 매번 다시 씀, (5) 점수를 고치면서 종합 점수는 갱신하지 않음, (6) 산술 오류까지 LLM 판단에 맡김.

## 2. 문제를 다시 정의한 이유

1차의 결론은 "평가와 코칭의 일관성을 확보하려면 검증 단계가 필요하다는 방향은 맞지만, LLM 한 번의 전체 재작성으로는 그 효과가 나오지 않았다"였습니다. 그래서 이번에는 질문을 바꿨습니다.

- 1차의 질문: Reviewer가 모순을 줄이는가?
- 2차의 질문: **검증해야 할 것들 가운데 무엇이 코드로 확정되고, 무엇이 의미 판단을 요구하는가?**

이렇게 나누면 1차의 실패가 다르게 보입니다. 산술 오류(0/10)는 LLM의 능력 문제가 아니라 LLM에게 맡길 일이 아니었습니다. 답변에 없는 근거(5/5 통과)는 판단력 문제가 아니라 판단에 필요한 입력이 없었던 것입니다. 정상 평가의 재작성(30/30)은 출력 형식이 재작성을 요구했기 때문입니다.

## 3. 개선된 파이프라인 구조

```
Evaluator 출력 (JSON 문자열)
   │
   ▼
① Deterministic Validator ─────── 코드, 호출 0회, 1ms 미만
   │   스키마, 필수 필드, 점수 범위 → 위반 시 중단
   │   종합 점수 = 5개 항목 평균 → 종합 점수만 수정
   │   목록 내 완전 중복 → 뒤의 것 제거
   ▼
② Context-Aware Reviewer ──────── LLM 1회
   │   입력: 질문, 답변 원문, 평가, Validator 결과
   │   출력: 발견 사항 목록 (문제 유형, 대상, 근거, 이유, 제안, 확신 수준)
   │   평가를 다시 쓰지 않음. 점수를 제안하지 않음. 문제가 없으면 빈 목록
   ▼
③ Controlled Correction ───────── 코드, 호출 0회
   │   게이트를 모두 통과한 발견 사항만 적용
   │   항목 점수는 변경 불가. 종합 점수는 코드로 재계산
   │   통과하지 못한 것은 보류하고 needs_review 로 기록
   │   수정이 적용된 경우에만 LLM을 한 번 더 호출해 새 문제가 생겼는지 점검
   ▼
Coach (운영 그대로)        변경이 없으면 Evaluator의 원문 문자열을 바이트 단위로 그대로 전달
```

## 4. 코드 검증과 AI 검증의 책임 분리

| 검증 대상 | 담당 | 이유 |
| --- | --- | --- |
| JSON 파싱, 스키마, 필수 필드, 타입 | 코드 | 참·거짓이 확정됨 |
| 점수 범위 (0~100) | 코드 | 〃 |
| 종합 점수 = 항목 평균 | 코드 | 산술 |
| 목록 내 완전 중복 | 코드 | 문자열 비교 |
| 항목 점수 변경 금지, 종합 점수 재계산 | 코드 | 불변 조건. LLM 출력에 의존하지 않음 |
| 발견 사항의 근거가 실제로 존재하는가 | 코드 | 인용 일치(v2.0) 또는 ID 유효성(v2.1) |
| 제안 문장에 답변에 없는 수치·영문 용어가 들어왔는가 | 코드 | 토큰 비교 |
| 점수와 서술이 반대 방향인가 | LLM | 문장의 긍정·부정 판단이 필요 |
| summary와 항목이 상충하는가 | LLM | 의미 비교 |
| 두 항목이 반대 사실을 말하는가 | LLM | 의미 비교 |
| 평가가 답변에 없는 사실을 인용하는가 | LLM | 답변 내용과의 대조 |
| 표현이 다른 두 항목이 같은 지적인가 | LLM | 의미 비교. 이번 실험에서 가장 크게 실패한 부분 (10절) |
| 고친 문장을 어떻게 쓸 것인가 | LLM이 제안, 코드가 채택 여부 결정 | |

종합 점수 계산 규칙은 서비스 구현에서 확인했습니다. Evaluator 프롬프트가 "overallScore를 logicalThinking, specificity, communication, jobFit, starStructure의 평균으로 계산하라"고 지시하고([tasks.py:139](../python/src/tasks.py#L139)), API가 이를 정수로 반환합니다. 그래서 기대값을 "5개 항목 평균의 반올림"으로 정의했습니다.

## 5. 실제 구현 내용

모두 [python/experiments/reviewer_validation_v2/](../python/experiments/reviewer_validation_v2/)에 있습니다.

### 5.1 Deterministic Validator (`validator.py`)

- `schemas.EvaluationResult` strict 검증, `overallScore` 정수 여부, 점수 범위 → 위반 시 `invalid`로 중단.
- 종합 점수가 평균의 반올림과 다르면 종합 점수만 수정하고 전후 값을 로그에 남김. 항목 점수는 건드리지 않음.
- 목록 내 완전 중복(공백·문장부호 무시)은 제거. 문자 유사도 0.8 이상인 유사 중복은 수정하지 않고 힌트로만 기록.
- 오프라인 검사 `test_offline.py`: 깨진 JSON, 필드 누락, 범위 초과, 문자열 점수, 산술 오류, 중복 입력에 대한 동작 확인.

### 5.2 Context-Aware Reviewer

운영과 같은 모델과 temperature(`gpt-4.1-mini`, 0.3)를 사용했습니다. 출력을 코드가 검사해야 하므로 CrewAI가 아니라 OpenAI SDK의 구조화 출력(스키마 강제)으로 호출했습니다.

| | v2.0 (`context_reviewer.py`) | v2.1 (`context_reviewer_v21.py`) |
| --- | --- | --- |
| 근거 제시 방식 | 평가와 답변의 문장을 글자 그대로 인용 | 코드가 답변 문장(A1…), 점수(S1…), 평가 조각(P1…)에 ID를 붙이고 Reviewer는 ID로 참조 |
| 처리 순서 | 발견 사항을 바로 반환 | 먼저 모든 조각에 대해 긍정·부정, 답변이 뒷받침하는지, 무엇과 상충하는지를 표시(claim_check)한 뒤 발견 사항 반환 |
| 점수 문제 | Reviewer가 `flag_score` 선택 | Reviewer는 어느 쪽이 틀렸는지만 표시. 점수 플래그의 유효성은 코드가 판정 |
| 중복 | 항목마다 삭제 제안 | 묶음(남길 것, 지울 것)으로 반환 |
| 호출 수 | 1회, 수정 적용 시 점검 1회 추가 (점검 결과는 기록만) | 1회, 수정 적용 시 1회 추가 (두 번째 결과도 같은 게이트로 적용) |

### 5.3 Controlled Correction (`correction.py`, `correction_v21.py`)

발견 사항마다 아래 게이트를 차례로 확인하고, 모두 통과한 것만 적용합니다.

| 게이트 | 내용 |
| --- | --- |
| G0 (v2.1) | Reviewer 자신의 사실 확인이 "답변이 뒷받침함"이라고 한 조각은 수정하지 않음 |
| G1 | 확신 수준이 high이고, 문장 수정 또는 항목 삭제일 것. 점수에 대한 지적은 적용하지 않음 |
| G2 | 대상 문장이 실제로 그 항목에 존재할 것 |
| G3 | 제시한 근거가 실제로 존재할 것 |
| G4 | 확인된 근거가 하나 이상 있을 것 (답변에 없는 사실 지적은 해당 문장에 답변에 없는 수치·영문 용어가 있으면 인정) |
| G5 | 제안 문장이 질문·답변·원래 문장에 없는 수치나 영문 용어를 새로 들여오지 않을 것 |
| G6 | 제안 문장이 비어 있지 않고 원래 문장보다 지나치게 길지 않을 것 |
| G7 | 삭제로 strengths나 weaknesses가 비지 않을 것 |

적용 후에는 항목 점수가 입력과 같은지 코드로 확인하고(`assert`), 종합 점수를 다시 계산합니다. 수정 내역은 `change_log`에 항목, 전후 문장, 이유와 함께 남습니다.

### 5.4 v2.0에서 v2.1로 고친 경위

v2.0의 프롬프트와 게이트를 동결하고 17건에 실행한 뒤, 실패 원인을 분석해 v2.1을 만들었습니다. v2.0 결과는 그대로 보존했습니다.

| v2.0에서 확인된 실패 (17건 실행) | 규모 | v2.1의 변경 |
| --- | --- | --- |
| 문장이 틀린 경우에도 Reviewer가 "점수가 틀림"을 선택해 수정이 보류됨 | 보류 25건 (TC-07 4/5, TC-10 5/5, TC-11 4/5 포함) | 어느 쪽이 답변과 어긋나는지만 표시하게 하고 조치는 그에 따라 결정 |
| 인용에 `항목.feedback=` 같은 라벨, 따옴표, 필드명만 적어 인용 검증에서 탈락 | 보류 11건 | 인용을 없애고 ID 참조로 변경 |
| 정상 평가(TC-06)의 summary를 모순으로 지적 | 5/5 지적, 2/5 수정 | 사실 확인 단계와 G0 추가 |
| summary의 한 구절(TC-16)을 놓침 | 탐지 0/5 | 조각 단위 사실 확인 |
| 중복 목록을 일부만 병합(TC-14) | 해소 2/5 | 중복 묶음 |

이 개정이 결과 해석에 주는 영향은 6.3절에 적었습니다.

### 6.3 판정 방법과 그 한계

세 가지를 함께 썼고 각각 따로 보고합니다.

1. **규칙 검사**: 1차의 `rule_checks`를 수정 없이 재사용.
2. **LLM Judge**: 1차와 같은 프롬프트, 같은 두 모델. 판정 근거 문장을 저장.
3. **AI-assisted adjudication**: 실험을 수행한 AI 코딩 에이전트가 최종 평가와 코칭을 읽고 1차와 같은 어휘(resolved / partial / not_resolved / preserved)로 판정. 판정마다 결정적인 문장을 인용해 [ai_assisted_adjudication.json](../python/experiments/reviewer_validation_v2/ai_assisted_adjudication.json)에 저장. **사람이 검토한 결과가 아닙니다.**

본문의 해소율, 보존율, 전파율은 3번 기준입니다. 새로 추가한 지표(탐지, 원문 유지, 보류 사유)는 실행 전에 [PREREGISTRATION.md](../python/experiments/reviewer_validation_v2/PREREGISTRATION.md)에 정의했습니다.

해석할 때 반드시 고려해야 할 점입니다.

- **v2.1의 17건 수치는 개발에 쓰인 데이터에 대한 값입니다.** v2.1은 같은 17건에서 v2.0이 실패한 것을 보고 만들었으므로 낙관적으로 나올 수 있습니다.
- **보조 케이스 8건(E4)은 v2.0 프롬프트를 동결한 뒤 작성했습니다.** v2.0의 E4 결과는 개발에 쓰이지 않은 데이터에 대한 값입니다. v2.1을 동결할 때는 E4의 v2.0 실행 로그 중 케이스별 규칙 판정 한 줄만 본 상태였고 출력 내용은 열지 않았습니다.
- 보조 케이스도 같은 작성자(AI 에이전트)가 만든 합성 데이터입니다.
- TC-08의 1차 규칙은 "구체성 점수가 60 이하로 내려가면 해소"입니다. 개선 구조는 점수를 바꾸지 않으므로 이 기준으로는 해소가 될 수 없습니다. 기준을 바꾸지 않고 미해소로 집계했습니다.

## 10. 새롭게 발견한 문제

① **LLM의 의미 중복 판단은 정상 평가를 손상시킵니다.** v2.1은 정상 케이스 30회 중 10회, 실제 Evaluator 출력 51건 중 18건에서 약점 항목을 삭제했고 그 대부분은 서로 다른 지적이었습니다. 기존 Reviewer도 중복 제거 지시를 받지만 이런 삭제는 관측되지 않았습니다. 삭제된 쌍의 문자 유사도는 0.08~0.52, 실제로 중복이던 쌍(TC-14, TC-15)은 0.35~0.77로 범위가 겹쳐 유사도 임계값 하나로 깔끔히 가를 수 없습니다.

② **"제거"가 맞는 자리에 "치환"을 적용하면 새 결함이 생깁니다.** v2.1은 TC-09에서 모순된 강점을 지우지 않고 "전달은 명확하지 않고 문장이 길어 핵심 파악이 어렵습니다"로 바꿔 strengths 목록에 남겼습니다(5/5). 모순은 사라졌지만 강점 목록에 비판이 들어갔습니다. 게이트는 문장의 사실 여부만 보고 그 문장이 놓일 자리와 맞는지는 보지 않습니다.

③ **LLM의 분류 결과를 코드 규칙에 넣으면 분류 오류가 그대로 판정 오류가 됩니다.** v2.1은 "피드백이 부정인데 점수가 75 이상이면 점수 플래그"를 코드로 도출합니다. Reviewer가 "전달은 명확하지만 … 설명은 빠져 있습니다" 같은 혼합 문장을 부정으로 분류하면 정상 평가에 플래그가 붙습니다(TC-02 5/5, 실제 출력에서 코드 도출 플래그 19개). 코드로 처리했다고 해서 확정적인 것이 아니라, 입력이 LLM 판단이면 그 불확실성을 물려받습니다.

④ **틀린 근거를 지우면 그 근거로 매겨진 점수가 근거 없이 남습니다.** TC-13에서 Kafka 관련 서술을 모두 지운 뒤에도 구체성 85점, 직무 적합성 85점은 그대로입니다. HO-05도 80점, 90점이 남았습니다. 점수 변경 금지 원칙의 직접적인 귀결이며, 이 상태를 처리하는 경로(예: Evaluator 재평가)는 구현하지 않았습니다.

⑤ **글자 그대로 인용하라는 요구는 지켜지지 않습니다.** v2.0에서 내용상 옳은 발견 사항 11건이 `specificity.feedback=…` 라벨, 따옴표, `strengths[0]` 같은 필드명 때문에 탈락했습니다. ID 참조로 바꾸자 이 유형은 사라졌지만, 없는 ID(`S10`)를 쓰거나 대상을 잘못 지정하는 오류가 새로 나타났습니다(HO-04).

⑥ **Reviewer는 조치 선택을 자주 틀립니다.** v2.0에서 문장이 틀린 경우에도 "점수가 틀림"을 고른 것이 25건이었습니다. 판단(어느 쪽이 답변과 맞지 않는가)과 조치(무엇을 할 것인가)를 한 번에 묻지 않고, 판단만 받고 조치는 코드가 정하게 하자 TC-07, TC-11이 개선됐습니다.

⑦ **"검토 필요" 표시가 과다합니다.** 17건 기준 v2.0 43/85, v2.1 29/85입니다. v2.0은 결함 케이스에서 보류가 많았기 때문이고, v2.1은 실제 Evaluator 출력에서도 20/51이었습니다. 이 비율이면 검토 대기열이 의미를 잃습니다.

⑧ **검증 수단의 한계는 그대로입니다.** 규칙 검사는 문구가 조금 바뀌면 해소로 오판합니다(HO-04: 기존 Reviewer가 "끝까지 제시되지 않아"를 "끝까지 명확히 제시되지 않아"로 바꾼 3회를 모두 해소로 판정. 판독은 미해소). `gpt-4o-mini` Judge는 코칭의 오류 전파에 대해 판독과 2~10/21만 일치했습니다. `gpt-4.1-mini` Judge는 수정이 명확한 v2.0 출력에서는 44/45 일치했지만 v2.1에서는 36/45였습니다.

⑨ **두 번째 판은 첫 번째 판의 실패를 보고 만들어졌습니다.** 같은 17건으로 고치고 같은 17건으로 재는 구조여서, 반복할수록 수치는 좋아지고 의미는 줄어듭니다. v2.1에서 멈춘 이유입니다.

이 판단을 합치면 다음 구조가 됩니다.

> Validator(코드) → 답변을 보는 Reviewer(ID 참조, 사실 확인, 모순과 근거 없는 서술만 지적) → 게이트를 통과한 문장 수정만 적용. 중복은 코드의 완전 일치만 처리. 점수 불일치는 표시만.

**이 조합 그대로는 실행하지 않았습니다.** v2.1에서 중복 병합과 점수 플래그 도출을 뺀 형태인데, 다시 돌리면 같은 17건에 세 번째로 맞추는 일이 되어 측정의 의미가 없다고 판단했습니다. 수집한 결과로 말할 수 있는 것은 제한적입니다. v2.1의 정상 케이스 손상 10건과 실제 출력 손상 18건은 해당 실행의 유일한 수정이 중복 병합이었으므로, 중복 병합이 없었다면 그 실행들은 원문 그대로 통과했을 것입니다. 반대로 TC-14, TC-15의 해소 9건도 중복 병합에서 나왔으므로 함께 사라집니다. 그 밖의 케이스가 어떻게 달라질지는 재실행 없이는 알 수 없습니다.

## 13. 실제 서비스에 적용할 가치가 있는지

**지금 적용할 가치가 있는 것**

- **Deterministic Validator.** 실제 Evaluator 출력 51건 중 7건의 종합 점수가 평균과 달랐고, 이는 사용자 화면에 그대로 나가는 숫자입니다. 코드 몇십 줄로 전부 고쳐지며 LLM 호출이 없습니다. 스키마 검증은 1차에서 지적한 "한 번이라도 형식이 깨지면 요청이 실패하는" 위험도 함께 막습니다.

**기존 Reviewer를 대체할 근거가 있는 것**

- **Validator + v2.0 방식의 Reviewer.** 실제 Evaluator 출력에서 기존 Reviewer는 3.8초를 쓰고 문장을 45/51 바꾸면서 산술 오류는 하나도 고치지 못했습니다. v2.0은 같은 입력에서 0.6초에 산술 오류 7건을 모두 고치고 나머지는 건드리지 않았습니다. 삽입 결함에 대한 해소율은 기존보다 낮지만(14/45 대 19/45), 실제 출력에서는 그런 결함이 드물었습니다(1차: 모순 0/51, Judge 기준). 다만 정상 평가의 summary를 잘못 고친 사례(TC-06, 2/30)가 있으므로, 처음에는 **자동 수정을 끄고 발견 사항만 기록하는 방식**으로 넣어 실제 데이터에서 무엇이 지적되는지부터 모으는 것이 안전합니다. 이 운영 방식 자체는 실험하지 않았습니다.

**아직 적용하면 안 되는 것**

- **v2.1 전체.** 결함 해소는 가장 높지만 실제 출력의 35%(18/51)에서 유효한 약점을 삭제했습니다. 사용자가 고칠 점을 이해하도록 돕는다는 서비스 목표에 비추면, 가끔 생기는 모순을 고치는 이익보다 정상 피드백을 지우는 손실이 큽니다.

**적용 전에 필요한 것**

- 개발에 쓰지 않은 더 큰 테스트 세트. 이번 보조 케이스는 8건뿐입니다.
- 실제 사용자 답변에 대한 Evaluator 출력에서 결함이 얼마나 자주 생기는지에 대한 측정. 드물다면 Validator만으로 충분할 수 있습니다.
- 사람의 판정. 이번 판정은 모두 AI-assisted adjudication입니다.
- 점수가 틀린 경우의 후속 경로 설계.

## 15. 면접에서 예상되는 기술 질문과 답변

**"코드로 검증할 것과 LLM에 맡길 것을 어떤 기준으로 나눴습니까?"**
같은 입력에 대해 참·거짓이 하나로 정해지는가입니다. 스키마, 점수 범위, 평균, 문자열 일치는 정해집니다. 두 문장이 반대 뜻인지, 평가가 답변에 없는 내용을 인용하는지는 의미를 읽어야 합니다. 실험에서 이 구분의 효과가 가장 분명했던 것은 산술 오류입니다. LLM Reviewer는 10번 중 한 번도 못 고쳤고 코드는 전부 고쳤습니다. 다만 경계가 생각보다 미묘하다는 것도 배웠습니다. "부정적 피드백인데 점수가 75 이상이면 플래그"는 코드 규칙처럼 보이지만 "부정적"이라는 분류가 LLM 출력이어서, 분류가 틀리면 규칙도 틀립니다. 실제 출력에서 이런 플래그가 19개 붙었습니다.

**"개선했다면서 정상 평가 보존율은 30/30에서 20/30으로 떨어졌네요."**
맞습니다. 개정판이 서로 다른 약점을 중복으로 보고 지웠기 때문입니다. 그래서 개정판 전체를 채택하지 않았습니다. 채택한 것은 Validator, 점수 불변 조건, 발견 사항 방식, 답변 원문 제공이고, LLM의 중복 병합은 뺐습니다. 처음 만든 판은 28/30이었고 실제 출력에서는 내용을 하나도 바꾸지 않았습니다.

**"첫 번째 개선안은 왜 기존보다 나빴습니까?"**
결함은 55번 중 50번 찾았습니다. 문제는 찾은 것을 적용하는 단계였습니다. 근거를 글자 그대로 인용하게 했는데 모델이 라벨이나 따옴표를 붙여 인용 검증에서 11건이 탈락했고, 문장이 틀린 경우에도 "점수가 틀렸다"고 분류해 25건이 보류됐습니다. 탐지와 수정을 따로 측정했기 때문에 원인을 구분할 수 있었습니다.

**"두 번째 판은 테스트 케이스에 맞춘 것 아닙니까?"**
그 위험을 인정합니다. 두 번째 판은 같은 17건의 실패를 보고 고쳤으므로 그 17건에 대한 수치는 낙관적입니다. 그래서 세 가지를 했습니다. 첫 번째 판의 결과를 지우지 않고 함께 보고했고, 프롬프트를 동결한 뒤 새 케이스 8건을 써서 따로 쟀고, 두 번째 판에서 반복을 멈췄습니다. 보조 케이스가 8건뿐이고 같은 작성자가 만들었다는 한계는 남습니다.

**"점수가 틀린 걸 알면서 왜 안 고칩니까?"**
Reviewer는 채점자가 아니기 때문입니다. 기존 Reviewer는 답변을 보지 않고 점수를 90에서 40으로 바꿨고 종합 점수는 갱신하지 않았습니다. 이번에는 점수를 코드로 잠그고 불일치만 표시하게 했습니다. 그 대가로 TC-08은 5/5에서 0/5가 됐습니다. 그리고 틀린 근거를 지운 뒤에도 그 근거로 매겨진 85점이 남는 문제를 새로 확인했습니다. 표시된 경우에 Evaluator를 다시 호출하는 경로가 필요하다고 보지만 구현하지 않았습니다.

**"코칭 오류 전파가 0/21이면 해결된 것 아닙니까?"**
그렇게 말할 수 없습니다. 인과가 분명한 것은 두 케이스입니다. 나머지는 Reviewer가 없어도 전파되지 않았거나 3번 중 1번만 나타난 편차였습니다. 그리고 각 경로에는 검증 단계의 첫 번째 실행 결과 하나가 들어갔습니다. 판독도 사람이 아니라 AI 에이전트가 했습니다.

**"LLM Judge를 못 믿는다면서 왜 또 썼습니까?"**
단독 근거로 쓰지 않았습니다. 규칙 검사, Judge 두 개, 출력을 읽은 판정을 함께 두고 어긋나는 곳을 그대로 적었습니다. 이번에도 규칙 검사가 문구만 살짝 바뀐 출력을 해소로 잘못 판정했고(HO-04), 작은 Judge 모델은 코칭 전파에 대해 판독과 21번 중 2~10번만 일치했습니다.

**"응답 시간은 오히려 늘었네요?"**
조건에 따라 다릅니다. 결함을 많이 넣은 17건에서는 개정판이 4.2초로 기존 2.8초보다 깁니다. 실제 Evaluator 출력에서는 첫 번째 판이 0.6초로 기존 3.8초보다 짧습니다. 문제가 없으면 빈 목록만 내기 때문입니다. 개정판은 모든 조각에 대해 사실 확인을 출력하므로 문제가 없어도 3.6초가 걸립니다. 정확도와 시간이 맞바뀌는 지점입니다.

**"이 구조를 실제로 배포한다면 어떤 순서로 하겠습니까?"**
Validator를 먼저 넣습니다. 위험이 없고 실제 출력의 14%에서 종합 점수를 바로잡습니다. 그다음 답변을 보는 Reviewer를 자동 수정 없이 기록 전용으로 넣어 실제 데이터에서 무엇이 지적되는지 모읍니다. 자동 수정은 그 데이터로 게이트를 검증한 뒤에 켭니다. 이 배포 순서는 제안이며 실험하지 않았습니다.

## 자기소개서 관점의 최종 분석

### Q1. 최초에는 어떤 문제를 해결하려고 했는가?

AI 면접 평가의 결과가 흔들리지 않게 하는 것, 즉 점수의 안정성입니다. 이것이 최초의 문제였다는 점과 그때 Self-Consistency를 검토했다는 점은 작성자의 설명이며 저장소로는 확인되지 않습니다. 저장소로 확인되는 것은 2026-07-30에 Reviewer를 포함한 4단계 구조가 구현됐다는 사실입니다.

### Q2. 실험을 통해 최초 문제 정의의 어떤 한계를 발견했는가?

두 단계에 걸쳐 드러났습니다.

- **1차**: 점수는 이미 안정적이었습니다(3회 평가 시 종합 점수 14/17 동일). 흔들리는 것은 설명 문장이었습니다(유사도 0.38). "점수 안정화"는 관측되지 않는 문제를 푸는 정의였습니다.
- **2차**: "평가와 코칭의 일관성"으로 바꾼 정의도 충분히 구체적이지 않았습니다. 일관성 문제 안에 성격이 다른 것들이 섞여 있었습니다. 산술 오류는 코드로 확정되는 문제였고, 답변에 없는 근거는 입력이 없어서 못 보던 문제였고, 문장 간 모순만이 의미 판단 문제였습니다. 하나의 LLM 단계에 모두 맡긴 것이 1차 실패의 원인이었습니다.

### Q3. AI가 제안한 방법 중 어떤 것을 받아들였고, 어떤 것을 받아들이지 않았는가?

과거의 제안 과정은 저장소에 없으므로, 실험으로 확인되는 것만 적습니다.

| 방법 | 채택 여부 | 근거 |
| --- | --- | --- |
| Self-Consistency (반복 평가 후 종합) | 받아들이지 않음 | 1차: 해결할 변동성이 작고 설명의 모순에 작용하지 않음 |
| Reviewer가 평가 전체를 다시 쓰는 방식 | 받아들이지 않음 | 1차: 해소 19/45, 코칭 차이 없음. 2차: 실제 출력 45/51의 문장을 바꾸면서 산술 오류 0건 수정 |
| 코드 기반 Validator | 받아들임 | 2차: 산술 오류 전부 수정, 호출 0회 |
| 답변을 보는 Reviewer + 발견 사항 + 게이트 수정 | 받아들임 | 2차: 원문 통과 44/51, 답변에 없는 근거 탐지 5/5 |
| LLM Reviewer의 중복 병합 제안 | 받아들이지 않음 | 2차: 실제 출력 18/51 손상 |
| LLM 분류에 기반한 점수 플래그 | 받아들이지 않음 | 2차: 정상 평가에 플래그 |
| LLM Reviewer의 문장 수정 제안 | 게이트를 통과한 것만 받아들임 | 2차: v2.0에서 발견 사항 89건 중 43건 적용, 46건 보류 |
| LLM Judge의 판정 | 단독으로는 받아들이지 않음 | 1차: 38/45 대 19/45. 2차: 모델과 조건에 따라 일치율 2/21 ~ 45/45 |

### Q4. AI의 결과를 그대로 신뢰하지 않고 검증한 구체적인 사례는 무엇인가?

1. **LLM Judge의 판정 (1차)**: "45회 중 38회 해소"라는 판정을 출력과 대조해 19회로 정정했습니다.
2. **Reviewer의 발견 사항 (2차)**: Reviewer가 낸 수정 제안을 그대로 적용하지 않고, 근거가 실제로 존재하는지, 제안 문장이 답변에 없는 수치나 용어를 들여오지 않는지를 코드로 확인한 뒤에만 적용했습니다. 예를 들어 오프라인 검사에서 "Kafka 도입으로 30% 절감했습니다"라는 제안은 답변에 없는 토큰 때문에 거부됩니다.
3. **자신이 만든 개선안 (2차)**: 개정판의 해소율(27/45)만 보지 않고 정상 케이스와 실제 출력에서 무엇이 바뀌었는지를 따로 확인해, 유효한 약점이 삭제되는 문제(18/51)를 찾았습니다.
4. **규칙 검사 (1차, 2차)**: 문구 일치 방식이 표현만 바뀐 출력을 해소로 오판하는 것을 두 번 확인했습니다(TC-11, HO-04).

2~4는 AI 코딩 에이전트가 설계하고 수행한 검증입니다.

### Q5. 문제를 어떻게 다시 정의했는가?

> "AI 평가 점수를 안정적으로 만든다"
> → (1차) "평가 근거와 코칭이 서로 어긋나지 않게 한다"
> → (2차) "검증해야 할 것 중 코드로 확정되는 것과 의미 판단이 필요한 것을 나누고, 각각을 맞는 수단에 맡긴다. LLM의 판단은 근거와 함께 받고 코드가 확인한 것만 반영한다"

### Q6. 새로운 문제 정의에 따라 어떤 기술적 선택을 했는가?

- 스키마, 점수 범위, 종합 점수 산술, 완전 중복을 코드로 검사하는 Validator를 LLM 앞에 둠.
- Reviewer의 입력에 질문과 답변 원문을 추가.
- Reviewer의 출력을 재작성된 평가에서 발견 사항 목록으로 변경. 점수 제안 금지.
- 발견 사항을 코드 게이트로 걸러 통과한 것만 적용하고, 나머지는 보류 사유와 함께 기록.
- 항목 점수는 코드의 불변 조건으로 잠그고 종합 점수는 코드로 계산.
- 변경이 없으면 원문 문자열을 그대로 전달.
- (개정판) 문장 인용 대신 코드가 부여한 ID로 참조, 발견 사항 전에 조각별 사실 확인.

### Q8. 최종적으로 어떤 설계가 적합하다고 판단했는가?

Validator(코드)를 항상 먼저 두고, 답변을 볼 수 있는 Reviewer가 발견 사항만 내며, 코드 게이트를 통과한 문장 수정만 적용하는 구조입니다. 점수는 코드로 잠급니다. LLM에 의한 의미 중복 병합과, LLM 분류에 기대는 자동 플래그는 넣지 않습니다. 서비스에는 Validator부터 적용하고, Reviewer는 자동 수정 없이 기록 전용으로 시작하는 것이 적합하다고 봅니다.

이 최종 조합은 이번에 그대로 실행하지 않았고, 배포 순서도 제안입니다.

### Q9. 실험 결과로 뒷받침되지 않는 주장은 무엇인가?

- 개선된 파이프라인이 기존 Reviewer보다 전반적으로 낫다. (지표에 따라 좋아진 것과 나빠진 것이 있음)
- 평가와 코칭의 일관성 문제를 해결했다. (인과가 분명한 것은 두 케이스)
- 결함 해소율을 42%에서 60%로 높였다. (27/45는 개발에 쓴 17건에 대한 값이고 정상 평가 손상을 동반함)
- 최종 권고 구조의 성능은 이러하다. (그 조합은 실행하지 않음)
- 응답 시간을 줄였다. (실제 출력과 v2.0 조합에서만. v2.1은 늘어남)
- 비용을 절감했다. (비용은 추정이며 v2.1은 증가)
- 평가의 정확도가 높아졌다. (정확도는 측정하지 않음. 점수는 바꾸지 않음)
- 사용자가 개선점을 더 잘 이해한다. (사용자 대상 측정 없음)
- 실제 운영 데이터로 검증했다. (합성 답변과, 그 답변에 대한 실제 Evaluator 출력)
- 사람이 결과를 검토했다. (판독은 모두 AI-assisted adjudication)
- 과거에 AI가 Self-Consistency를 제안했고 이를 검토 끝에 기각했다. (저장소에 기록 없음)
- 이 결과가 일반적으로 성립한다. (기존 17건, 보조 8건)
