## 요약

1. **Self-Consistency가 겨냥하는 문제는 이 서비스에서 거의 관측되지 않았습니다.** 같은 답변을 Evaluator에 3회 평가했을 때 종합 점수는 17개 답변 중 14개에서 세 번 모두 같았고, 차이가 난 3개도 최대 5점이었습니다. 반면 평가 문장은 실행마다 크게 달랐습니다(문자 유사도 평균 0.38). 점수는 안정적이고 설명이 흔들리므로, 점수를 여러 번 뽑아 종합하는 방식은 해결 대상이 맞지 않습니다.
2. **Reviewer는 정상 평가를 망가뜨리지 않았습니다.** 정상 평가 30회와 Evaluator의 실제 출력 51회에서 점수를 바꾼 경우는 0회였습니다.
3. **그러나 Reviewer가 삽입된 결함을 해소한 것은 45회 중 19회(42%)였습니다.** 목록 수준의 결함(strengths에 낀 모순, 중복 항목)은 잘 고쳤고, 종합 의견(summary)에 들어간 모순, 항목 간 사실 모순, 종합 점수 산술 오류는 거의 고치지 못했습니다.
4. **Reviewer를 거쳐도 코칭의 일관성은 달라지지 않았습니다.** 삽입된 오류가 코칭까지 전파된 횟수는 Reviewer 없이 4/14, Reviewer를 거쳐 4/14로 같았습니다. Reviewer는 호출 1회와 약 3초(전체의 약 23%)를 추가합니다.
5. **검증 도구 자체도 검증이 필요했습니다.** LLM Judge(gpt-4.1-mini)는 45회 중 38회를 "해소됨"으로 판정했지만 출력을 직접 읽으면 19회였습니다.

결론: "점수 변동성이 아니라 평가 근거와 코칭의 일관성이 문제"라는 **문제 재정의는 실험 결과와 부합**합니다. 다만 그 해법으로 구현된 **현재 Reviewer가 그 문제를 충분히 해결한다는 근거는 이번 실험에서 나오지 않았습니다.** 상세 판단은 12절에 있습니다.

모든 비율은 합성 케이스 17건에서 나온 값이며, 일반적인 성능 수치로 해석할 수 없습니다.

## 1. 실험 목적

InterviewBridge가 지향하는 것은 면접 평가 점수를 안정적으로 내는 것이 아니라, 사용자가 무엇을 고쳐야 하는지 이해할 수 있도록 평가 근거와 코칭 내용이 서로 어긋나지 않게 하는 것입니다. 이 목표에 대해 두 가지 접근을 실행으로 비교했습니다.

- **Self-Consistency**: 같은 답변을 여러 번 평가해 종합한다. 겨냥하는 문제는 평가 결과의 변동성.
- **Reflection / Reviewer**: Evaluator의 평가를 별도 Agent가 검토한 뒤 Coach에 넘긴다. 겨냥하는 문제는 평가 내부의 모순, 중복, 누락.

두 방식은 같은 문제의 대체재가 아니므로 승패를 가리지 않고, 각각 어떤 문제를 해결하고 어디서 한계가 있는지를 분리해 확인했습니다.

### 2.2 Agent와 데이터 흐름

```
Question Analyzer → Answer Evaluator → Reviewer(Reflection) → Coach
   (자유 텍스트)        (JSON)              (JSON)             (JSON)
```

| 요소 | 실제 구현 |
| --- | --- |
| Question Analyzer | 질문 의도, 핵심 역량, 질문 유형, STAR 권장 여부를 자유 텍스트로 출력. 프롬프트에 `{question}` 이 없고 `question_generation_task` 의 출력을 컨텍스트로 받음 ([tasks.py:57-103](../python/src/tasks.py#L57-L103)) |
| Answer Evaluator | 논리성, 구체성, 전달력, 직무 적합성, STAR 구조 5개 항목의 점수와 피드백, summary, strengths, weaknesses를 JSON으로 출력. `overallScore` 는 5개 항목의 평균으로 계산하라고 지시 ([tasks.py:139](../python/src/tasks.py#L139)) |
| Reviewer | 아래 2.3 참조 |
| Coach | 종합 요약, 개선 팁 최대 4개, 모범 답안(모국어·면접 언어), 다음 연습 질문을 JSON으로 출력. 컨텍스트는 Analyzer 출력과 Reviewer 출력 ([tasks.py:380-383](../python/src/tasks.py#L380-L383)) |
| STAR 평가 기준 | 별도 루브릭 없음. Evaluator 규칙의 한 항목이자 5개 점수 항목 중 하나 |
| Structured Output | `schemas.py` 에 Pydantic 모델이 정의되어 있지만 Task에 연결되어 있지 않음(`output_pydantic` 미사용). JSON 형식은 프롬프트 지시로만 요구하고 [api.py:79-82](../python/api.py#L79-L82) 에서 `json.loads` 로 파싱 |
| Agent 간 전달 | CrewAI `context=[...]`. 앞 Task의 원문 출력(raw 문자열)이 다음 Task 프롬프트에 붙음 |
| 테스트 코드 | Python 쪽 없음. Backend는 `contextLoads` 1건 |
| 실행 환경 | Python 3.11.9 가상환경(`python/llm`), `python/.env` 의 `OPENAI_API_KEY` |

### 2.3 Reviewer가 실제로 하는 일

코드로 확인한 사실입니다([agents.py:107-132](../python/src/agents.py#L107-L132), [tasks.py:227-265](../python/src/tasks.py#L227-L265)).

- **입력은 Evaluator의 출력뿐입니다.** 프롬프트에 `{question}`, `{answer}` 가 없어 면접 질문과 답변 원문을 보지 못합니다.
- **지적 목록을 내지 않고 평가 JSON 전체를 다시 써서 반환합니다.** 무엇을 왜 고쳤는지는 남지 않습니다.
- **Reviewer의 출력이 곧 사용자에게 보이는 최종 평가입니다.** `api.py` 는 Evaluator가 아니라 Reviewer의 출력을 `evaluation` 으로 응답합니다([api.py:78-79](../python/api.py#L78-L79)).
- **점수를 바꾸는 것을 막는 규칙이 없습니다.** "다시 평가하지 말 것"과 "논리적 불일치를 수정할 것"이 함께 있어, 점수 수정이 허용되는지는 프롬프트만으로는 정해지지 않습니다. 실험에서는 85회 중 5회 점수를 바꿨습니다(7절).
- `overallScore` 가 5개 항목의 평균이어야 한다는 규칙은 Evaluator 프롬프트에만 있고 Reviewer 프롬프트에는 없습니다.

운영 파이프라인과 다른 점은 다음과 같습니다.

- 실험 1, 2의 Evaluator 출력은 실제 Evaluator가 만든 것이 아니라 손으로 쓴 합성 평가입니다.
- Reviewer 없는 경로(A안)에서는 Coach의 두 번째 컨텍스트 자리에 Evaluator 출력을 넣었습니다. Coach 프롬프트의 "reviewed evaluation"이라는 표현은 양쪽 모두 그대로입니다.
- Analyzer에는 질문을 `question_generation_task` 의 출력 자리에 넣어 주었습니다(질문 생성 직후 분석하는 정상 흐름을 재현).

### 6.2 판정 기준 (실행 전에 정의)

**실험 1 (Reviewer 단독)**

| 기준 | 방법 |
| --- | --- |
| 형식 준수 | `json.loads` 성공, `schemas.EvaluationResult` strict 검증 통과, `overallScore` 가 int |
| 점수 변경 | 5개 항목 점수와 `overallScore` 의 전후 비교 |
| 결함 해소 (규칙) | 모순: 오류 문구(marker)가 남아 있지 않음 / TC-08: 구체성 점수 60 이하 / 중복: strengths·weaknesses 개수가 기준 이하 / TC-17: `overallScore` 와 평균의 차이 1 이하 |
| 결함 해소 (Judge) | 질문, 답변, 원본·수정 평가, 삽입한 오류 설명을 주고 해소 여부, 의미 변경 여부, 새 문제 여부를 판정 |

**실험 2 (Coach 일관성)**

| 기준 | 방법 |
| --- | --- |
| C1 형식 | `json.loads` + `schemas.CoachingResult` 검증, 팁 4개 이하 |
| C2 평가와의 모순 | Judge: 코칭이 평가의 의도된 해석과 상충하는 서술을 하는가 |
| C3 오류 전파 | Judge + 규칙: 삽입된 잘못된 서술을 코칭이 반복하거나 그 위에 조언을 세우는가 |
| C4 약점 반영 | Judge: 케이스별 핵심 약점 중 팁이 다룬 비율 |
| C5 근거 없는 조언 | Judge: 평가의 어떤 약점에도 대응하지 않는 팁의 수 |
| C6 구체성 | Judge: 1~5점 |
| C7 지어낸 수치 | 규칙: 모범 답안에 답변 원문에 없는 숫자가 등장 |

Judge는 어느 경로(A/B)의 출력인지 모르는 상태로 판정했습니다.

### 6.3 실행 후에 추가한 것 (사전 계획과 다른 점)

투명성을 위해 계획과 달라진 부분을 적습니다.

1. **직접 판독을 최종 기준으로 추가했습니다.** 실행 초기에 규칙 검사와 Judge가 실제 출력과 다르게 판정하는 사례가 확인됐습니다(7.4절). 그래서 실험 1의 85회 전부와 실험 2의 28회를 직접 읽어 판정하고, 판정마다 결정적인 문장을 인용해 [manual_adjudication.json](../python/experiments/reviewer_validation/manual_adjudication.json)에 남겼습니다. 사전에 정한 규칙은 고치지 않았고, 규칙·Judge·판독 결과를 모두 따로 보고합니다.
2. **Judge 모델을 변경했습니다.** 원래 계획한 `gpt-4.1` 이 403으로 막혀 5절의 두 모델로 바꿨습니다.
3. **반복 횟수와 범위를 늘렸습니다.** 비용이 예상보다 낮아 실험 1을 케이스당 2회에서 5회로, 실험 3을 6개 답변에서 17개 답변 전체로 확대했습니다. 먼저 나온 결과를 보고 줄이거나 제외한 실행은 없습니다.

직접 판독은 이 검증을 수행한 AI 코딩 어시스턴트가 했습니다. 판정 근거가 CSV의 `manual_evidence` 열에 인용되어 있으므로 작성자가 직접 다시 확인할 수 있습니다.

### 7.3 질문별 답

**① 모순을 정확하게 발견했는가?** 위치에 따라 달랐습니다. strengths·weaknesses 목록에 들어간 모순(TC-09)과 점수와 해당 항목 피드백이 정면으로 어긋난 경우(TC-08)는 5회 모두 고쳤습니다. summary 문장에 들어간 모순(TC-07, TC-16)은 10회 중 한 번도 고치지 못했고, 서로 다른 항목이 반대 사실을 말하는 경우(TC-10, TC-11)는 10회 중 1회만 완전히 고쳤습니다.

**② 중복을 발견했는가?** strengths·weaknesses 목록의 중복은 10회 중 8회 완전히 병합했습니다. 5개 항목 피드백에 같은 지적이 반복되는 것(TC-14)은 5회 모두 그대로 두었습니다.

**③ 누락된 평가 근거를 발견했는가?** 아니오. 구조상 할 수 없습니다. Reviewer는 답변 원문을 받지 않으므로 평가가 답변과 맞는지 대조할 수 없습니다. 답변에 없는 Kafka와 비용 30% 절감을 근거로 든 평가(TC-13)는 5회 모두 그대로 통과했습니다. 일반론뿐인 평가(TC-12)는 5회 모두 일반론으로 남았고, 없는 내용을 지어낸 경우는 없었습니다.

**④ 정상 평가를 불필요하게 수정했는가?** 점수와 의미는 30회 모두 유지했습니다. 다만 글자 그대로 둔 경우는 0회로, 문제가 없어도 매번 문장을 바꿔 썼습니다("없음"을 "부족함"으로 바꾸는 식의 표현 변경).

**⑤ 점수를 임의로 변경했는가?** 85회 중 5회, 모두 TC-08입니다. 바꾼 방향(90 → 40)은 실제 답변과 맞지만, Reviewer는 답변을 보지 못하므로 40이라는 값은 피드백 문장만 보고 정한 것입니다. 이때 `overallScore` 를 함께 고치지 않아 새 불일치를 만들었습니다.

**⑥ 출력 형식이 기존 시스템과 호환되는가?** 85회 모두 `json.loads` 와 스키마 검증을 통과했습니다.

### 7.4 검증 수단의 신뢰도

같은 45회에 대해 세 가지 수단이 낸 "해소됨" 판정을 직접 판독과 비교했습니다.

| 수단 | "해소됨"으로 판정 | 직접 판독과 일치 |
| --- | --- | --- |
| 직접 판독 | 19/45 | 기준 |

- `gpt-4.1-mini` Judge는 TC-07에서 summary가 "논리적 구성이 뛰어나며"로 남아 있는데도 5회 모두 "해소됨"으로 판정했습니다. 근거 문장에는 "리뷰어는 summary를 그대로 유지하면서 … 모순을 해소했습니다"라고 적었습니다.

## 9. Self-Consistency 비교 결과 (실험 3)

17개 답변을 운영 Evaluator에 3회씩 평가했습니다(51회). 이 실험의 평가는 합성이 아니라 Evaluator가 실제로 만든 출력입니다. 원본은 [exp3_self_consistency_by_case.csv](../python/experiments/reviewer_validation/results/exp3_self_consistency_by_case.csv)에 있습니다.

### 9.1 점수 변동성

| 지표 | 값 |
| --- | --- |
| 3회의 종합 점수가 모두 같은 답변 | 14/17 |
| 종합 점수 범위(최대−최소)의 최댓값 | 5점 |
| 종합 점수 범위의 평균 | 0.53점 |
| 항목 점수 범위 분포 (17답변 × 5항목 = 85) | 0점 50건, 5점 24건, 10점 11건 |
| 항목 점수 범위의 평균 | 2.7점 |
| Evaluator 형식 준수 | 51/51 |

점수는 5점 단위로 출력됐고, 항목 점수가 5~10점 움직여도 평균인 종합 점수는 대부분 같았습니다.

### 9.2 평가 근거의 차이

같은 답변에 대한 3회 평가의 문장을 서로 비교한 문자 유사도는 평균 0.38이었습니다(답변별 0.27~0.53). 점수는 거의 같은데 설명 문장은 매번 다르게 쓰였습니다. 유사도는 표현의 차이를 재는 값이어서, 지적하는 약점의 내용이 달라졌는지는 이 수치만으로는 알 수 없습니다.

### 9.3 종합 방식과 그 결과

실행 전에 정한 방식은 다음과 같습니다. 항목 점수는 3회의 중앙값, 종합 점수는 그 5개 중앙값의 평균, 문장은 중앙값에 점수가 가장 가까운 실행 하나에서 통째로 가져옵니다.

| 지표 | 값 |
| --- | --- |
| 종합 결과의 종합 점수가 1회차 평가와 다른 답변 | 4/17 (최대 4점) |
| 그중 변동성 때문에 달라진 것 | 2건 (TC-05, TC-10) |
| 그중 종합 점수를 평균으로 다시 계산하면서 달라진 것 | 2건 (TC-06, TC-13) |
| 종합 후 점수와 문장의 출처가 어긋난 답변 | 1/17 (TC-10의 STAR 항목: 점수는 중앙값 80, 문장은 75점짜리 평가의 것) |

Self-Consistency는 점수를 종합할 수는 있지만 문장은 종합할 수 없어 결국 한 실행의 문장을 골라 써야 합니다. 그 과정에서 점수와 설명이 서로 다른 실행에서 온 조합이 생길 수 있고, 이번에도 1건 관측됐습니다. 즉 평가와 설명의 일관성이라는 목표에 대해서는 효과가 없을 뿐 아니라 새 불일치의 원인이 될 수 있습니다.

### 9.4 실제 Evaluator 출력에 결함이 얼마나 있는가

| 지표 | 값 | 방법 |
| --- | --- | --- |
| 내부 모순이 있는 평가 | 0/51 | Judge 2종 모두 0건. Judge의 한계는 7.4절 참조 |
| `overallScore` 가 5개 항목 평균과 2점 이상 다른 평가 | 5/51 (차이 2~4점) | 규칙 (산술) |
| 그 5건 중 Reviewer가 바로잡은 것 | 0/5 | 규칙 |
| Reviewer가 점수를 바꾼 평가 | 0/51 | 규칙 |
| Reviewer 전후 문장 유사도 | 평균 0.98, 최소 0.91 | 규칙 |
| Reviewer 형식 준수 | 51/51 | 규칙 |

실제 Evaluator 출력에서는 Reviewer가 겨냥하는 종류의 모순이 관측되지 않았고, Reviewer는 문장을 조금 다듬는 것 외에 한 일이 없었습니다. 유일하게 확인된 실제 결함인 종합 점수 산술 오류 5건은 Reviewer가 하나도 고치지 못했습니다.

### 9.5 두 방식이 해결하는 문제의 구분

| | Self-Consistency | Reviewer |
| --- | --- | --- |
| 해결 대상 | 실행 간 점수 차이 | 한 평가 안의 모순과 중복 |
| 이번에 관측된 문제의 크기 | 종합 점수 범위 평균 0.53점 | 실제 출력에서 모순 0/51 (Judge 기준), 산술 오류 5/51 |
| 이번에 관측된 효과 | 종합 점수가 달라진 답변 2/17 (변동성 기인) | 합성 결함 해소 19/45, 실제 산술 오류 해소 0/5 |
| 하지 못하는 것 | 평가 문장의 모순 해소. 평가와 코칭의 일치 | 답변 원문과의 대조. 평가의 정확도 향상 |
| 부작용 | 점수와 문장 출처 불일치 1/17 | 점수 변경 시 종합 점수 미갱신 5/5 (TC-08) |

Self-Consistency가 점수 변동을 줄인다고 해서 평가와 코칭의 모순이 줄어든다는 근거는 없습니다. Reviewer가 모순을 줄인다고 해서 평가가 답변에 비추어 더 정확해진다는 근거도 없습니다. 이번 실험은 두 주장 중 어느 것도 뒷받침하지 않습니다.

CrewAI의 `kickoff().token_usage` 는 호출별 값이 아니라 LLM 객체의 누적값을 Agent 수만큼 더한 값입니다. 운영 코드는 Agent 4개가 LLM 객체 하나를 공유하므로, 운영 crew를 한 번 실행하면 실제 요청 4건이 16건으로, 두 번째 실행에서는 32건으로 보고됩니다. 이 실험은 LLM 객체의 카운터를 호출 전후로 차분해 측정했습니다. 이후 이 프로젝트에서 비용을 볼 때 `token_usage` 를 그대로 쓰면 4배 이상 과대 계상됩니다.

## 11. 실패 사례와 한계

### 11.1 Reviewer의 실패 사례

| 사례 | 내용 |
| --- | --- |
| summary의 모순을 통과 | 가장 전형적인 모순(논리성 35점 + "논리적 구성이 매우 뛰어남")을 5회 모두 고치지 못했고, 이 문장은 코칭 요약에 그대로 전파됨 |
| 모순을 없애지 않고 흐리게 함 | "전혀 없어"를 "부족해"로 바꿔 모순이 덜 눈에 띄게만 만든 경우 3/5 (TC-10) |
| 종합 점수 산술 오류를 통과 | 합성 5/5, 실제 Evaluator 출력 5/5 모두 미수정 |
| 수정하면서 새 불일치 생성 | 항목 점수를 고치고 `overallScore` 는 그대로 둠 5/5 (TC-08) |
| 답변과 대조 불가 | 답변에 없는 사실을 근거로 든 평가를 5/5 통과시켰고, 그 내용이 모범 답안에 지원자 경험으로 서술됨 4/4 |
| 수정 내역이 남지 않음 | JSON 전체를 다시 쓰므로 무엇을 고쳤는지 출력만으로 알 수 없음. 문제가 없어도 문장을 매번 바꿈 (정상 30회 중 원문 유지 0회) |

### 11.2 실험의 한계

- **표본이 작습니다.** 합성 케이스 17건, 결함 유형당 2~3건입니다. 여기서 나온 비율은 이 케이스들에 대한 관측값이며 일반적인 탐지율로 볼 수 없습니다.
- **결함은 인위적으로 삽입한 것입니다.** 실제 Evaluator 출력 51건에서는 같은 종류의 모순이 관측되지 않았으므로, 합성 결함이 실제 운영에서 얼마나 자주 생기는지는 알 수 없습니다.
- **Judge가 약합니다.** 평가 대상과 같은 모델(`gpt-4.1-mini`)과 더 작은 모델(`gpt-4o-mini`)밖에 쓸 수 없었고, 직접 판독과의 일치율이 58%, 36%였습니다. 실험 2의 약점 반영, 근거 없는 조언, 구체성 수치와 9.4절의 "모순 0/51"은 이 Judge에 의존합니다.
- **직접 판독은 한 번, AI 어시스턴트가 했습니다.** 근거 인용은 남겼지만 사람이 독립적으로 재판정하지는 않았습니다.
- **실험 2는 경로당 2회 반복입니다.** Coach의 실행 간 편차와 경로 간 차이를 통계적으로 구분할 수 없습니다.
- **Self-Consistency는 3회, temperature 0.3, 짧은 합성 답변에서만 측정했습니다.** 긴 답변, 다른 temperature, 다른 모델에서는 변동성이 다를 수 있습니다.
- **평가의 정확도는 측정하지 않았습니다.** 사람 면접관의 평가와 비교한 적이 없으므로 점수가 옳은지는 이 실험의 범위 밖입니다.
- **사용자가 실제로 더 잘 이해하는지는 측정하지 않았습니다.** 서비스 목표인 "사용자의 이해"는 사용자 연구가 필요하며, 이 실험은 그 대리 지표인 텍스트 일관성만 봤습니다.
- **응답 시간은 로컬에서 OpenAI API를 호출한 값입니다.** Spring Boot 경유 구간과 네트워크 조건은 포함하지 않았습니다.

### 11.3 실험 중 발견한 범위 밖 이슈 (수정하지 않음)

1. **Analyzer가 질문을 직접 받지 않습니다.** 프롬프트에 `{question}` 이 없고 모듈 전역 객체인 `question_generation_task` 의 출력에 의존합니다. 서버 시작 후 질문 생성 없이 `/analyze` 가 호출되면 질문 없이 분석합니다. 운영 crew를 그대로 실행한 3회 중 "새 기술을 빠르게 배운 경험"을 묻는 질문에 대해 Analyzer가 "도전적인 상황을 어떻게 해결했는지"로 분석한 것을 관측했습니다. 코드 구조상 여러 사용자가 동시에 쓰면 다른 사용자가 마지막으로 생성한 질문이 컨텍스트로 들어갈 수 있습니다(이 경우는 실행해 보지 않았습니다).
2. **Structured Output이 강제되지 않습니다.** `schemas.py` 의 모델이 Task에 연결되어 있지 않고 `/analyze` 에 `response_model` 이 없습니다. 이번 실험에서는 Evaluator 51회, Reviewer 136회, Coach 68회 모두 형식이 맞았지만, 한 번이라도 깨지면 `json.loads` 예외로 요청이 실패합니다.
3. **항목 점수의 척도가 프롬프트에 없습니다.** "Overall Score (0-100)"만 명시되어 있습니다.
4. **Python 쪽 자동 테스트가 없습니다.**

| ⑤ 모범 답안의 수치를 답변 원문과 대조하는 검사를 둔다 | 지어낸 수치 약 1/3. Reviewer와 무관한 Coach의 문제 | 규칙 검사로 탐지 가능함은 확인(오탐 1건). 차단 효과는 미검증 |

정리하면, **"반복 평가로 점수를 안정화"하는 대신 "평가와 코칭 사이에 검증 단계"를 둔다는 선택의 방향은 실험과 부합하지만, 그 검증 단계를 LLM 한 번의 전체 재작성에 맡긴 현재 구현은 목표한 효과를 보이지 못했습니다.** 다음 단계는 검증 단계를 없애는 것이 아니라, 코드 검사와 답변 원문을 보는 Reviewer로 나누어 다시 설계하고 같은 테스트 세트로 재측정하는 것입니다.

## 13. 자기소개서에 활용 가능한 검증된 사실

시간순으로 구분합니다.

### 13.1 과거의 설계 (저장소로 확인되는 것)

- 2026-07-30 커밋 `4660aaa` 에서 Evaluator와 Coach 사이에 Reviewer(Reflection Agent)를 둔 4단계 구조를 구현했다.
- 2026-07-31 커밋 `29682b3` 에서 평가와 코칭 출력을 JSON으로 바꾸고 Reviewer가 같은 형식을 유지하도록 했다.
- Reviewer에게 "답변을 다시 평가하지 말 것", "점수와 서술의 일관성 확인", "중복 제거"를 지시했고, Coach에게 "검토된 평가만 사용할 것", "언급되지 않은 수치를 지어내지 말 것"을 지시했다.
- Self-Consistency는 저장소에 구현된 적이 없다.

### 13.2 과거의 설계 동기 (저장소로 확인되지 않는 것)

- Self-Consistency를 검토했다는 사실, AI가 그것을 제안했다는 사실, 채택하지 않은 당시의 이유는 저장소에 기록이 없습니다. 자기소개서에 쓴다면 본인의 기억과 당시 자료(대화 기록 등)에 근거해야 하며, 이 보고서는 그 부분을 증명하지 않습니다.

### Q4. 기존의 문제 정의를 어떻게 바꾸면 실제 구현과 실험 결과에 가장 부합하는가?

실험 결과와 어긋나지 않는 문제 정의는 다음과 같습니다.

> 주어진 문제는 "AI 평가 점수가 흔들리지 않게 하라"였다. 측정해 보니 점수는 이미 안정적이었고(3회 반복 시 14/17 동일), 실제로 흔들리는 것은 점수를 설명하는 문장이었다. 사용자가 무엇을 고쳐야 하는지는 점수가 아니라 설명과 코칭에서 나오므로, 문제를 "평가 근거와 코칭이 서로 어긋나지 않게 하는 것"으로 다시 정의했다.

여기에 실험이 요구하는 단서가 하나 붙습니다.

> 그 해법으로 둔 Reviewer를 검증해 보니, 정상 평가는 해치지 않았지만 삽입한 모순의 42%만 해소했고 코칭 결과를 바꾸지 못했다. 검증 단계를 두는 방향은 유지하되, 구현은 코드 검사와 답변을 볼 수 있는 Reviewer로 나누어야 한다는 결론에 이르렀다.

"Reviewer를 도입해 일관성을 확보했다"로 쓰면 실험 결과와 맞지 않습니다.

### Q6. 자기소개서에 사용할 만한 가장 설득력 있는 사실 3개는 무엇인가?

1. **문제 재정의의 근거**: 같은 답변을 3회 평가하면 종합 점수는 17개 중 14개에서 동일했지만 평가 문장의 유사도는 평균 0.38이었다. 흔들리는 것은 점수가 아니라 설명이었다.
2. **AI의 판정을 그대로 받아들이지 않은 근거**: LLM Judge는 Reviewer가 모순을 45회 중 38회 해소했다고 판정했지만, 출력을 직접 읽은 결과는 19회였다. "논리성 35점 + 논리적 구성이 뛰어남"이 그대로 남은 출력을 Judge는 5회 모두 해소로 판정했다.
3. **자신의 설계를 검증해 한계를 찾은 근거**: Reviewer 유무에 따른 코칭의 오류 전파는 4/14로 같았다. Reviewer가 고친 결함은 Reviewer 없이도 코칭에 전파되지 않았고, 전파된 결함은 Reviewer가 고치지 못한 것이었다. 원인은 Reviewer가 답변 원문을 보지 못하고 평가 전체를 다시 쓰는 구조에 있었다.

세 사실 모두 "합성 케이스 17건 기준"이라는 범위와 함께 써야 합니다.

### Q7. 현재 결과로는 주장할 수 없는 내용은 무엇인가?

- Reviewer를 도입해 평가와 코칭의 일관성이 향상됐다. (차이가 관측되지 않음)
- Reviewer가 평가의 정확도를 높였다. (정확도는 측정하지 않았고, Reviewer는 답변을 보지 못함)
- Reviewer의 모순 탐지율은 N%다. (17건의 합성 케이스에서 나온 값이며 일반화할 수 없음)
- Self-Consistency는 효과가 없다. (이 조건에서 해결할 변동성이 작았다는 것만 확인. 다른 모델, temperature, 긴 답변에서는 측정하지 않음)
- 사용자가 개선점을 더 잘 이해하게 됐다. (사용자 대상 측정 없음)
- 실제 운영 데이터에서 검증했다. (전부 합성 데이터)
- Self-Consistency를 검토하고 기각한 과정이 기록으로 남아 있다. (저장소에 없음)
- 12.3절의 재설계안이 효과가 있다. (산술 검사 외에는 구현하지 않음)
- 비용을 N% 절감했다. (비용은 공개 단가 기준 추정이며, 절감을 구현한 적 없음)

### Q8. 면접관이 이 설계를 비판한다면 어떤 질문을 할 수 있으며 어떻게 답해야 하는가?

**"Reviewer가 효과 없다는 결과 아닌가요? 왜 넣었습니까?"**
현재 구현이 코칭 결과를 바꾸지 못한 것은 맞습니다. 다만 실험으로 확인한 것은 두 가지입니다. 평가의 결함이 Coach를 거쳐 사용자에게 도달한다는 것(삽입한 모순이 코칭 요약에 4회 중 4회 전파)과, 지금의 Reviewer는 그중 일부만 막는다는 것입니다. 그래서 결론은 검증 단계를 빼는 것이 아니라 다시 설계하는 것입니다. 코드로 판정되는 것은 코드로 검사하고, Reviewer에는 답변 원문을 주고, 전체 재작성 대신 발견 사항을 내게 하는 방향입니다. 이 재설계는 아직 검증하지 않았습니다.

**"테스트 케이스 17건으로 무엇을 말할 수 있습니까?"**
일반적인 성능 수치는 말할 수 없습니다. 말할 수 있는 것은 실패의 유형입니다. 5회 반복에서 5회 모두 같은 방식으로 실패한 케이스(summary 모순, 산술 오류, 답변과의 대조 불가)는 우연이 아니라 구조에서 오는 문제로 볼 근거가 됩니다. 비율은 범위를 밝혀서만 씁니다.

**"합성 결함은 현실적입니까? 실제 Evaluator가 그런 모순을 냅니까?"**
실제 Evaluator 출력 51건에서는 같은 종류의 모순이 관측되지 않았습니다. 실제로 나온 결함은 종합 점수 산술 오류 5건이었고 Reviewer는 이를 고치지 못했습니다. 즉 Reviewer가 겨냥한 문제는 이 조건에서는 드물고, 실제로 생기는 문제는 Reviewer가 풀지 못하는 종류였습니다. 이것이 재설계가 필요하다고 본 이유 중 하나입니다.

**"LLM Judge를 믿을 수 없다면 무엇으로 판정했습니까?"**
세 가지를 함께 썼습니다. 실행 전에 정한 규칙 검사, 모델이 다른 Judge 두 개, 그리고 출력을 직접 읽은 판정입니다. 셋이 어긋난 지점을 그대로 보고했고(일치율 80%, 58%, 36%), 최종 수치는 근거 문장을 인용해 둔 직접 판독을 기준으로 했습니다. 직접 판독이 한 번뿐이라는 것은 한계로 적었습니다.

**"Self-Consistency를 3회만 돌리고 기각하는 것은 성급하지 않습니까?"**
기각한 이유는 표본 크기가 아니라 대상이 다르다는 점입니다. Self-Consistency는 점수를 종합하지만 이 서비스의 목표는 설명과 코칭의 일치입니다. 문장은 평균을 낼 수 없어서 한 실행의 것을 골라 써야 하고, 그 과정에서 점수와 문장의 출처가 어긋난 사례도 1건 나왔습니다. 변동성 측정(14/17 동일)은 그 판단을 뒷받침하는 보조 근거이며, temperature가 높거나 답변이 길면 결과가 다를 수 있다는 점은 확인하지 않았습니다.

**"Reviewer가 점수를 바꾸는 것은 '다시 평가하지 말라'는 지시와 모순 아닙니까?"**
맞습니다. 프롬프트에 "다시 평가하지 말 것"과 "불일치를 수정할 것"이 함께 있고 점수 수정에 대한 규칙은 없습니다. 실험에서 Reviewer는 85회 중 5회 점수를 바꿨고, 그때마다 종합 점수를 갱신하지 않아 새 불일치를 만들었습니다. 점수를 바꿀 권한을 줄지, 준다면 종합 점수를 누가 다시 계산할지를 명시해야 합니다.
