# 2차 실험 사전 정의

테스트 케이스에 대해 개선 파이프라인을 한 번도 실행하기 전에 작성했습니다.
이 시점까지 개선 파이프라인은 데이터셋에 없는 임시 예시 1건으로만 호출했습니다(총 4회, 동작 확인용).

## 동결한 것

- Context-Aware Reviewer 프롬프트: `context_reviewer.SYSTEM_PROMPT`, SHA-256 `61e9f6c8275b48f3aae857c8a8ae628a7cf1366ccd9800c6d1f1366da185631d`
- Controlled Correction 게이트 G1~G7: `correction.py` 머리말
- Validator 규칙과 임계값(유사 중복 0.8): `validator.py` 머리말
- 결함 위치 정의: `prereg.DEFECT_FIELDS`

임시 예시로 확인하면서 고친 것은 두 가지이며 모두 인용 형식 처리입니다.
(1) 근거 인용을 문자열 하나에서 목록으로 변경, (2) 인용 앞에 붙는 `항목.feedback=` 같은 라벨을 코드에서 제거.

## 1차와 같은 기준으로 비교하는 것

| 지표 | 정의 | 1차 값 | 분모 |
| --- | --- | --- | --- |
| 삽입 결함 해소 | 1차와 같은 판정 어휘(resolved / partial / not_resolved)로 최종 평가 JSON을 판독 | 19/45 | 탐지 가능 결함 9건 × 5회 |
| 정상 평가 보존 | 점수와 의미가 그대로 | 30/30 | 정상 6건 × 5회 |
| 점수 변경 | 5개 항목 점수 또는 종합 점수가 입력과 다름 | 5/85 | 전체 |
| 종합 점수 산술 오류 | 최종 평가에서 종합 점수와 평균의 차이가 1 초과 | 수정 0/5 (TC-17), 신규 발생 5 (TC-08) | |
| 답변에 없는 근거 | TC-13 최종 평가에 Kafka, 30% 가 남음 | 5/5 통과 | TC-13 × 5회 |
| 코칭 오류 전파 | 1차와 같은 7개 케이스의 코칭을 판독 | 4/14, 4/14 | 7건 × 반복 |

| LLM Judge | 1차와 같은 프롬프트, 같은 두 모델 | 38/45, 22/45 | |

`test_cases.json` 은 수정하지 않습니다. 기대 동작과 규칙 필드도 그대로 씁니다.

주의: TC-08의 1차 규칙은 "구체성 점수가 60 이하로 내려가면 해소"입니다. 개선 구조는 점수를 바꾸지 않도록 설계했으므로 이 기준으로는 해소로 집계될 수 없습니다. 기준을 바꾸지 않고 미해소로 집계하며, 탐지 여부는 아래 새 지표로 따로 보고합니다.

## 새로 추가하는 지표

| 지표 | 정의 |
| --- | --- |
| 탐지 | 결함 위치(`prereg.DEFECT_FIELDS`)에 대한 발견 사항이 하나 이상 있음 (적용 여부 무관). 산술 케이스는 Validator 수정 로그 |
| 자동 적용 / 보류 | 발견 사항이 게이트를 통과해 적용됐는지, 어떤 게이트에서 보류됐는지 |
| 정상 평가의 원문 유지 | 최종 평가 문자열이 입력과 바이트 단위로 같음 |
| 정상 평가에 대한 발견 사항 | 정상 케이스와 실제 Evaluator 출력에서 나온 발견 사항 수 (오탐 후보) |
| 사후 점검 잔여 | 수정 적용 후 재검토에서 나온 발견 사항 수 |
| 검토 필요 상태 | 보류 또는 잔여 발견 사항이 있는 실행의 비율 |

## 판독

출력을 읽고 내리는 판정은 이 실험을 수행하는 AI 코딩 에이전트가 하며 **AI-assisted adjudication** 으로 표기합니다.
사람이 검토한 결과가 아닙니다. 판정마다 근거 문장을 인용해 `ai_assisted_adjudication.json` 에 남깁니다.

# 추가: 개정판 v2.1 (v2.0 실행 후 작성)

v2.0을 동결한 채 기존 17건에 실행한 결과(`results/e1_main_runs.json`), 탐지는 됐지만 자동 수정으로 이어지지 않는 설계 결함이 확인됐습니다. 그 실패 분석을 근거로 개정판을 만들었습니다. v2.0 결과는 그대로 보존하고 보고합니다.

## v2.1에서 바꾼 것

| v2.0에서 확인된 문제 (17건 실행) | v2.1의 변경 |
| --- | --- |
| 인용에 라벨, 따옴표, 필드명만 적어 인용 검증에서 탈락 (11건) | 코드가 문장, 항목, 점수, 답변 문장에 ID를 붙이고 Reviewer는 ID로만 참조 |
| 문장이 틀린 경우에도 `flag_score` 를 선택 (TC-07, TC-10, TC-11) | Reviewer는 어느 쪽이 답변과 어긋나는지만 밝히고, 점수 플래그는 코드가 판정 |
| 정상 평가 오탐 (TC-06), summary 구절 미탐지 (TC-16) | 발견 사항보다 먼저 조각별 사실 확인(claim_check)을 수행. 답변이 뒷받침하는 조각은 수정 대상이 될 수 없음 (게이트 G0) |
| 목록 중복이 일부만 병합 (TC-14) | 중복을 묶음(keep / remove)으로 반환 |
| 사후 점검에서 나온 지적을 적용하지 않음 | 두 번째 호출의 지적도 같은 게이트로 한 번 더 적용 (최대 2회 호출) |

동결: `context_reviewer_v21.SYSTEM_PROMPT` SHA-256 `e96649937c8a600c0e7de26f0fa393d0f92867a7f435e460ba143baec95884db`, 게이트는 `correction_v21.py` 머리말.
v2.1도 테스트 케이스가 아닌 임시 예시로만 동작을 확인했습니다(호출 8회). 그 과정에서 고친 것: 근거 ID에 대상 자신이나 없는 ID가 섞이면 무시, 점수 플래그의 방향 검사(S1)와 코드 도출(S2) 추가.

## 이 개정이 결과 해석에 주는 영향

- v2.1은 기존 17건의 v2.0 실패를 보고 만들었습니다. 따라서 **17건에 대한 v2.1 수치는 개발에 쓰인 데이터에 대한 값**이며 낙관적으로 나올 수 있습니다.
- 보조 케이스 8건(E4)은 v2.0으로 이미 한 번 실행됐습니다. v2.1을 동결하는 시점까지 그 결과는 실행 로그의 요약 한 줄(케이스별 규칙 판정)만 보았고 출력 내용은 열어보지 않았습니다. v2.1 설계는 17건의 분석만으로 정했습니다. E4의 v2.1 결과가 개발에 쓰이지 않은 데이터에 가장 가까운 값입니다.
- 지표 정의, 테스트 케이스, 기대 동작은 바꾸지 않았습니다.
